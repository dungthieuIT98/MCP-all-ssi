3Flow: đăng nhập lần đầu (Device Code Flow)

1
Client gọi tools/call lần đầu (chưa có token). auth-proxy kiểm tra token_valid() = 0, refresh thất bại → khởi động Device Code Flow.
2
auth-proxy sinh api_key (nếu chưa có), POST tới Azure AD /devicecode, nhận user_code + verification_uri, rồi trả message cho client: "Truy cập microsoft.com/devicelogin, nhập code…, API Key: …".
3
User mở browser, nhập code, đăng nhập Azure AD. Song song, background task của auth-proxy poll /token (grant device_code) đến khi user hoàn tất.
4
Azure trả access_token + refresh_token → lưu Postgres theo api_key (kèm claims upn/email).
5
Client dán api_key vào header X-Api-Key và gọi lại tool — từ đây mọi request được tự động gắn Bearer token, hết hạn thì auto-refresh.

4Flow: một câu SQL

1
Client → Kong → auth-proxy: tools/call execute_query {query} kèm X-Api-Key.
2
auth-proxy lấy Azure token từ Postgres theo api_key (refresh nếu hết hạn), forward tới trino-mcp kèm Authorization: Bearer + Mcp-Session-Id (per-user). Gặp 400 Invalid session → tự re-initialize và retry 1 lần.
3
trino-mcp validate JWT với JWKS Azure AD (issuer sts.windows.net/{tenant}, audience = client id). Không hợp lệ → 401.
4
Guard tầng app: isReadOnlyQuery() chỉ cho SELECT/SHOW/DESCRIBE/EXPLAIN/WITH, chặn multi-statement. Impersonation: claim email → X-Trino-User (session user thật trong Trino).
5
Trino thực thi với access control read-only (rules.json — lớp phòng thủ thứ 2) trên catalog MySQL, trả kết quả JSON ngược về client.

5Flow: tool Superset

1
Tool superset_* tới auth-proxy → đổi Azure token lấy Superset JWT qua POST /api/v1/security/azure_login (cache RAM 4h).
2
Superset tự verify Azure JWT (JWKS, RS256, issuer, audience), map claim email → user đã tồn tại trong Superset (không auto-provision, không có → 403), mint FAB JWT per-user.
3
auth-proxy forward tool call tới superset-mcp kèm Bearer = Superset JWT + session per-key → superset-mcp gọi REST API bằng đúng identity/roles/RLS của user thật.

6Lưu ý quan trọng

  • Identity = api_key (migration 004_api_key_identity.sql): api_key là PRIMARY KEY của user_tokens, không còn cột username. proxy.py lấy identity trực tiếp từ giá trị header X-Api-Key — key chưa có row nghĩa là chưa login, sẽ được đưa vào device-code flow.
  • Header định danh thống nhất là X-Api-Key trên toàn bộ code + docs (README cũ còn nhắc token cache file JSON — thực tế token lưu Postgres).
  • Gọi thẳng :6275 không kèm key → chạy identity _local (fallback dev) — production nên chặn, chỉ cho vào qua Kong.
  • State device-flow nằm trong RAM — restart auth-proxy giữa lúc login thì phải xin code mới (token đã cấp vẫn bền trong Postgres).
  • api_key là bearer credential: ai cầm là thành user đó — cần HTTPS + cân nhắc rotation khi ra ngoài localhost.
