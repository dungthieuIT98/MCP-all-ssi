Components

Python

auth-proxy

OAuth 2.1 reverse proxy — single gateway for both mcp-trino and mcp-superset. Runs device code flow against Azure AD, caches tokens, auto-refreshes, then injects Bearer token before forwarding. Manages two separate downstream sessions.

:6275 (listen):6274 → mcp-trino:8000 → mcp-superset

Stack: Starlette · httpx · msal · uvicorn

Modules: mcp_handlers · trino_handlers · superset_handlers · superset_auth

Go

mcp-trino

MCP server exposing Trino SQL engine. Validates Azure AD Bearer token on every request. Supports STDIO and StreamableHTTP transports. Enforces read-only SQL and user impersonation via JWT claims.

:8080 (STDIO):6274 (HTTP)

Auth-Proxy — Internal Call Routing (mcp_handlers.py)

Routing logic (mcp_handlers.handle_tools_call):
1. Kiểm tra token_state["access_token"] — nếu thiếu → khởi động device code flow → trả về login message
2. Kiểm tra token_valid() — nếu hết hạn → gọi refresh_token() → nếu refresh fail → xóa token → restart device code
3. Route theo tên tool: tool trong _SUPERSET_TOOL_NAMES → superset_handlers; còn lại → trino_handlers
4. tools/list: forward đến mcp-trino lấy Trino tools, merge với SUPERSET_TOOLS static list
Azure AD device code flow (khi chưa có token)
Route đến trino_handlers
Route đến superset_handlers
Trả login message khi chưa auth

Azure AD OIDC — Device Code Flow (Chi tiết)

Token lifecycle đầy đủ:
Acquire: device_code flow → access_token (JWT, ~1h) + refresh_token → cache vào token_state trong memory
Validate: token_valid() decode JWT base64, kiểm tra exp claim — hết hạn khi còn dưới buffer time
Refresh: khi hết hạn → refresh_token(grant_type=refresh_token) → Azure trả access_token mới → update cache
Re-auth: nếu refresh fail (invalid_grant / interaction_required) → xóa token → restart device code flow
User identity: JWT payload decode (base64) lấy upn / email / preferred_username → dùng cho Trino user impersonation và Superset OAuth login

Superset — Token Exchange & MCP Forwarding

Dual-token strategy: mcp-trino nhận Azure AD JWT trực tiếp · mcp-superset nhận Superset JWT (được exchange từ Azure token)
Cache key: hash(azure_token) (không lưu raw token) · TTL 4h · buffer 60s · fallback sang admin credentials nếu OAuth chưa cấu hình
Session recovery: 400 "session" → reset _superset_mcp_session_id=None → reinitialize → retry 1 lần

Trino — Token Injection & Session Management (trino_handlers.py)

Token injection: mọi request đến mcp-trino đều được inject Authorization: Bearer <azure_jwt> + Mcp-Session-Id
Session recovery: 400 "Invalid session" → _reinitialize() gửi initialize message → lấy session-id mới → retry request
User impersonation: mcp-trino decode JWT lấy upn/email → set Trino user → audit logs reflect real caller
SQL logging: proxy log SQL query khi tool là execute_query hoặc explain_query

Security Architecture

Read-Only Enforcement

mcp-trino parses every SQL statement, blocks non-SELECT operations before reaching Trino. Enforced at the Go layer — cannot be bypassed by the proxy.

OAuth 2.1 / Azure AD

auth-proxy implements device code flow via msal. Tokens are cached in-memory, auto-refreshed. Clients never handle credentials directly.

User Impersonation

mcp-trino decodes JWT, extracts upn/email/preferred_username → forwards as Trino user identity → row-level security and audit logs reflect the real caller.

Token Stripping

auth-proxy strips any client-provided auth headers and injects fresh Azure AD Bearer tokens before forwarding — prevents token spoofing from the client side.

Dual-JWT Isolation

mcp-trino accepts only Azure AD JWTs. mcp-superset accepts only Superset JWTs. Token exchange is internal to auth-proxy — neither downstream sees the other's token.

Network Isolation

All Docker services run on internal trino-net bridge. Only mapped ports are exposed to host. mcp-superset accessible only from auth-proxy.
